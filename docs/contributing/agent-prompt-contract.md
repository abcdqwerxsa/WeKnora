# Agent Prompt 设计契约

> 适用对象：WeKnora / LuoSA 项目里所有 `builtin_agents.yaml` 注册的内置 Agent 及其对应的 system prompt。
>
> **核心立场**：Agent 是**通用型 RAG Agent**，不绑定特定租户 / 知识库 / 业务场景。
>
> 适用未来任何用户、任何业务域、任何 KB 配置。

---

## 1. 三层边界划分

| 层 | 谁负责 | 放什么 |
|---|---|---|
| **prompt 层**（`config/prompt_templates/system_prompt.yaml`）| 系统维护者 | 通用任务定义 + 通用规则 + 通用检索策略 + 降级行为 |
| **config 层**（`config/builtin_agents.yaml`）| 系统维护者 | 通用参数（`agent_mode` / `temperature` / `allowed_tools` / `kb_selection_mode`）|
| **运行时层**（用户在 UI 里操作）| 用户 / 租户 | 具体 KB 选择、文档上传、标签、文件夹、会话绑定 |

**核心原则：低层不应该依赖高层的数据。**

- prompt 不知道 KB 里有什么。
- yaml 不知道用户的 KB ID。
- 这两层都不绑定业务域 / 行业 / 公司。

---

## 2. prompt 层允许 / 禁止清单

### ✅ prompt 层可以包含

- 任务描述（"做什么"）："对文档做四维度审查"
- 行为规则（"怎么做"）："置信度 < 0.7 不报告"、"必须挂源"
- 工具描述："使用 `knowledge_search`、`grep_chunks`"
- 通用检索策略："对所有已绑定 KB 做统一全文检索（向量 + BM25 + 重排序）"
- 降级行为："KB 检索为空时如何处理"
- 通用输出格式模板（用占位符 `<文档名>` `<资质证书>` 而非具体名）
- 反例说明（"不要列不存在的 KB"——这种反例是合法的）

### ❌ prompt 层禁止包含

| 类别 | 例子 |
|---|---|
| 具体 KB 命名约定 | `KB_TYPO_DICT`、`KB_BID_TEMPLATE`、`KB_DOC_TEMPLATE` 等虚构 KB 名 |
| 具体公司 / 客户名 | 任何真实公司名（即使是 demo 数据） |
| 具体业务域术语 | "算力服务器"、"工程设计"等垂直行业黑话 |
| 具体形近字 / 术语对照表 | "账/帐、做/作、象/像、度/渡、地/得/的" |
| 具体法规 / 标准名 | "《民法典》第 585 条"（除非是通用示例） |
| 具体文档示例 | "卡莱特响应书 §3"（用占位符代替） |
| 变更痕迹 | "修订版"、"v2"、"基于 X 反馈" |
| 部署状态 | "当前部署了 X 个 KB"、"用户 KB 里有什么" |
| 用户 KB 描述 | "用户有合同 KB / 资质 KB" |

---

## 3. config 层允许 / 禁止清单

### ✅ config 层（`builtin_agents.yaml`）可以包含

- `agent_mode`（`smart-reasoning` / `quick-answer` / `workflow`）
- `temperature` / `max_iterations` / `max_completion_tokens`
- `allowed_tools`（工具白名单）
- `kb_selection_mode`（`all` / `selected` / `none`）
- `skills_selection_mode`（`all` / `explicit`）
- `sandbox_config_id`（具体沙箱 ID 是技术配置）
- `system_prompt_id`（指向通用 prompt 模板）
- `display_group`、`question_suggestions` 等 UI 元数据
- i18n 翻译（6 种语言：`default` / `zh-CN` / `zh-TW` / `en-US` / `ja-JP` / `ko-KR`）

### ❌ config 层禁止包含

- 具体 KB ID（不能用 `kb_ids: ["5b199e25-..."]` 这种硬编码）
- 业务域限制（"仅 IT 行业"、"仅工程领域"）
- 用户特定的资源引用（"租户 X 的工作空间"、"用户 Y 的偏好"）

---

## 4. 运行时层（用户负责）

- 创建 / 选择哪些 KB
- 上传什么文档（合同 / 标书 / 论文 / 报告 / ...）
- 给文档打什么标签、建什么文件夹
- 在会话里绑定哪些 KB
- 选择模型（对话模型 / 向量模型 / 重排模型 / 多模态）

**这些选择由用户在 UI 里决定，不应该被 prompt / yaml 限制。**

---

## 5. 自检 5 问

每次修改 prompt / config 后，跑这 5 个问题自检。任何一条回答"否"，都需要清理。

| # | 自检问题 | 期望 |
|---|---|---|
| 1 | 把 prompt 给一个**完全不相关行业**的用户看，能理解吗？ | ✅ 应该能 |
| 2 | 把 prompt 给一个**没有 KB** 的用户看，能用吗？ | ✅ 应该能用（降级模式） |
| 3 | 把 prompt 给一个**100 个 KB** 的用户看，能用吗？ | ✅ 应该能用（全检索） |
| 4 | 把 prompt 给一个**未来新建的租户**看，能直接用吗？ | ✅ 应该能直接用 |
| 5 | 把 prompt 翻译成英文，语义保持吗？ | ✅ 应该保持 |

---

## 6. 反模式对照表

| ❌ 错误写法（绑定型） | ✅ 正确写法（通用型） |
|---|---|
| "检索 KB_TYPO_DICT 易错字库" | "对已绑定 KB 做全文检索" |
| "账 / 帐、做 / 作、形近字对照..." | （不列规则，让 LLM 用自身能力） |
| "用户 KB 里的卡莱特响应书" | （不引用具体文档） |
| "适用于 IT 算力采购投标" | "适用于任何文档审查场景" |
| "基于 v2 修订版的当前部署" | （无版本痕迹） |
| "若 KB_BID_HISTORY 缺失则..." | "若知识库中无相关内容则..." |
| 在 yaml 里写 `kb_ids: [<具体 uuid>]` | 用 `kb_selection_mode: "all"` 让用户自己绑 |
| 报告示例里写"账务处理 → 账务处理" | 报告示例里写"<原文片段> → <建议改法>" |

## 7. 设计决策的边界判断

写 prompt 时遇到不确定的内容，按这个流程判断：

```
这条 prompt / 配置在 10 个不同业务域的用户面前都能用吗？
├── 是 → 继续
└── 否 → 调整到通用

这条规则需要 LLM 自身能力 vs 注入特定知识？
├── LLM 自身能力（如中文理解、逻辑推理）→ 不要写在 prompt 里
└── 特定知识（如"账/帐 区别"）→ 让 LLM 从 KB 检索得到，不写在 prompt 里

这条规则如果 KB 内容变了，prompt 是不是也要改？
├── 是 → 违反通用原则，改成"由 KB 决定"
└── 否 → 可以保留
```

---

## 8. 例外与边界说明

### 反例引用是合法的

prompt 中可以出现"反例说明"，例如：

- "不要列出不存在的 KB（如 ❌ KB_TYPO_DICT）—— 这些不是真实 KB，永远不要提"
- "不要凭空假设 KB 内容（如'基于某个易错字库，账/帐应改为...'）—— 只能引用检索到的实际文档"

这类反例明确告诉 LLM "不要做 X"，**不绑定到任何特定场景**，因此是允许的。

### 通用占位符是合法的

报告中可以出现占位符：

- `<文档名>` / `<资质证书>` / `<历史投标文件>` / `<filename>` —— 这些是 schema 占位符，不是具体内容。

### 通用示例是合法的

工具调用示例可以用通用术语：

```yaml
# ✅ 合法
"prompt": "请从 {start_id@query} 中抽取评分项"

# ❌ 非法
"prompt": "请从卡莱特响应书里抽取评分项"
```

## 10. 协作约定

- **修改 prompt / yaml 前**：先读本文档
- **修改 prompt / yaml 后**：跑自检 5 问
- **Code Review**：reviewer 必须按本文档的允许 / 禁止清单逐条核对
- **新增 builtin agent**：必须满足本契约的全部约束
- **如有争议**：以"通用化"为默认原则，例外需在 PR 描述里说明

---

**文档维护**：本文档随项目演进。任何变更需团队 review 后合并。
