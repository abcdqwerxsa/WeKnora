# 上线路径与验收标准

## 1. 上线节奏（建议 5 周）

| 周次 | 工作内容 | 交付物 |
|------|---------|--------|
| W1 | 13 个 Agent YAML 入库 + 4 个工作流 JSON 通过 API 导入 + KB 草稿准备 | `builtin_agents.yaml` 增补 PR、4 个工作流跑通空流程 |
| W2 | KB 内容收集（模板 / 术语 / 历史案例首批 ≥ 100 篇） | `KB_COMPANY_TEMPLATE`、`KB_BID_HISTORY` 等首批入库 |
| W3 | 用历史样本回归 4 个工作流，记录 prompt/参数调优点 | `wf-eval-report.md`（每个工作流 20+ 样本） |
| W4 | 小范围灰度（2 个租户 / 3 类文档） | 灰度反馈表 + 修复 patch |
| W5 | 全量上线 + 培训 + 文档交付 | 培训视频 / PPT、上线公告 |

## 2. 验收标准

### 2.1 功能层

| 模块 | 验收指标 | 目标值 |
|------|---------|--------|
| 文档审查（格式） | 格式问题召回率 | ≥ 95%（对比人工审查） |
| 文档审查（校对） | 中文错别字识别 F1 | ≥ 0.85 |
| 文档审查（一致性） | 金额/日期冲突识别 F1 | ≥ 0.80 |
| 招投标比对 | 评分项不漏检率 | 100%（每条评分项都有判定） |
| 招投标比对 | 风险标注精度 | ≥ 90%（人工复核通过率） |
| 知识文档生成 | "待填占位符" 不遗漏率 | 100%（不允许把待填项编造掉） |
| 知识库入库 | 元数据完整率 | ≥ 98% |
| 主动提醒 | 历史问题召回率 | ≥ 0.80（Top5 含相关历史） |

### 2.2 性能层

| 指标 | 目标 |
|------|------|
| 单文档审查（≤ 50 页）端到端延迟 | ≤ 60 秒 |
| 单次招投标比对（≤ 200 评分项）端到端延迟 | ≤ 5 分钟 |
| 单次方案生成（含 1 轮校核）端到端延迟 | ≤ 90 秒 |
| 单次入库（≤ 50 MB）端到端延迟 | ≤ 30 秒 |
| 主动提醒单次响应 | ≤ 15 秒 |

### 2.3 安全 / 合规层

- 所有生成类 Agent 在 system_prompt 中固化"不编造"硬约束，**已通过自动化测试断言至少 3 个诱导 prompt 不会产出未标占位的关键数据**
- HITL 节点不可跳过：每个工作流的 `Answer` 节点模板必须包含 `{{待确认}}` 字样，由人工在前端勾选后才视为完成
- 风险等级为 `high` 的结论必须人工二次确认，否则不写入最终报告

## 3. 风险与回退方案

| 风险 | 概率 | 影响 | 回退方案 |
|------|------|------|---------|
| 模板库覆盖不全，格式审查误报多 | 高 | 中 | 阈值调高（仅报 `severity=high`），其余走人工 |
| 评分表结构复杂，结构化 Agent 漏项 | 中 | 高 | 引入"两遍提取"机制：第一遍启发式 + LLM，第二遍仅 LLM，对比差异 |
| 生成 Agent 编造业绩 / 资质 | 中 | 高（合规风险） | 在 Answer 模板里强制列出 `{{待填}}` 项；校核 Agent 强制 `pass` 才出 Answer |
| 长文档超时 | 中 | 中 | 分块并行（每个 Workflow 拆成 N 个 sub-workflow 并发跑） |
| KB 内容质量差，检索召回噪音大 | 中 | 中 | 调高 `vector_threshold` 到 0.6；按 `source` 元数据过滤 |
| 用户不熟悉 Workflow DSL | 高 | 低 | 提供 UI 模板（WorkflowList 提供"复制示例"按钮） |

## 4. 监控与可观测性

| 维度 | 工具 |
