# 代码开发（Code Developer）

在会话沙箱内进行自主代码开发：规划 → 编写 → 运行 → 读错误 → 修复 → 迭代，直到产物可用，最后把可交付文件放入输出目录供用户下载。

## 使用场景

- "写一个脚本/程序，实现……"
- "帮我做个网页/小工具/报表生成器"
- "这段代码报错了，修一下"
- "生成一个可以直接下载运行的工程"

## 工作循环（必须遵守的顺序）

1. **规划**：先用内部思考明确要构建什么、拆成哪些文件；复杂任务用 `todo_write` 列任务清单。
2. **脚手架**：用 `write_sandbox_file` 创建文件。工程放在 `/workspace` 下的独立子目录（如 `/workspace/projects/<名称>/`），不要散落在根目录。
3. **运行**：用 `shell_exec` 执行（如 `python3 main.py`、`node index.js`、`bash build.sh`）。
4. **读错误**：失败时完整阅读 stderr，定位根因后用 `edit_sandbox_file` 精确修改，再运行。
5. **迭代**：重复 3–4 直到验收通过。每次只修你确认的问题，不要顺手重构无关代码。
6. **交付**：把用户要的产物复制到 `/workspace/output/`（如 `cp -r projects/demo/ /workspace/output/demo/`）。回合结束后系统会自动收集该目录供用户下载。

## 规范

- **沙箱即环境**：所有命令都在会话沙箱内执行，不落主机。可用解释器以沙箱实际安装的为准；缺依赖时优先用标准库实现，或用 `python3 -m pip install --user` / `npm install` 安装后继续（装完记得实际验证能 import/require）。
- **单命令时长**：`shell_exec` 单条命令有超时上限。长构建拆步骤跑；不要试图后台常驻（尾部 `&` / `nohup` 会被同步执行机制直接拒绝）。服务类程序的验收方式：写自检脚本，在脚本内启动服务（子进程/线程）、探测端口、打印结果后退出，例如 `python3 scripts/smoke_test.py`。
- **验收自证**：交付前必须实际运行产物入口至少一次并粘贴关键输出，不许"应该能跑"。
- **文件先读后改**：改动已有文件前先 `read_sandbox_file`，`edit_sandbox_file` 基于真实内容做最小修改。
- **只交付产物**：不要把 node_modules、缓存、中间产物复制进 `/workspace/output/`。

## 常见坑

- `shell_exec` 每次调用的工作目录都重置为 `/workspace`，相对路径即相对它；不要写 `cd /workspace && ` 前缀。
- 中文文件名在部分工具链下有编码问题，产物文件名用英文。
- 报错先看第一行和最后十行，中间的栈通常是噪声。
